# Watcher-Cron 설계 규약

이 문서는 `no-agent` cron과 유사한 무인 워처가 안전하게 동작하기 위한 규약입니다.

## 핵심 원칙

### 1. Discord 폴링은 리액션 전용

메시지 텍스트와 첨부의 수신·처리는 실시간 에이전트만 소유합니다. 워처는 ✅·⛔ 같은
리액션만 폴링합니다. 읽기 전용 인덱서처럼 메시지를 소비하지 않는 작업만 예외로 허용합니다.

### 2. 자격증명은 명시적으로 전달

cron 환경에는 시크릿이 자동 주입되지 않는다고 가정합니다. 워처는 비공개 시크릿 파일 또는
승인된 비밀 공급자에서 값을 읽고, 자격증명이 필요한 자식 프로세스에는 `env=`로 명시 전달합니다.
자식의 숨은 폴백에 의존하지 않습니다.

### 3. 런타임 루트와 의존성

배포된 래퍼는 `AUTOPHAGY_RUNTIME_ROOT` 같은 환경 변수 또는 공용 리졸버로 런타임 루트를
해석합니다. 하드코딩된 개인 경로를 쓰지 않습니다. 외부 의존성은 lazy import하고, 불가하면
명확히 fail-closed로 종료합니다.

### 4. 상태는 성공 뒤에 기록

대상을 claim한 뒤 작업하고, 성공한 경우에만 완료 기록을 남깁니다. 실패하면 claim을 해제해
재시도가 가능해야 합니다. 변이가 성공한 뒤 알림이 실패한 경우에는 변이 완료 상태를 되돌리지
않고 알림 오류만 관측합니다.

## 승인 메시지 생명주기

동일한 논리 요청에는 승인 메시지를 정확히 하나만 유지합니다.

1. producer와 watcher가 같은 키별 lease를 획득합니다.
2. 기존 `message_id`를 조용히 덮어쓰지 않습니다. 교체가 필요하면 메시지를 명시적으로
   supersede하고 레코드를 compare-and-swap으로 제거한 뒤 새로 게시합니다.
3. 이미 ✅ 또는 ⛔가 있는 메시지는 producer가 건드리지 않고 watcher에 양보합니다.
4. 메시지 생존이나 해시 바인딩을 확인할 수 없으면 `DEFER` 또는 `REFUSE`합니다.
5. 저장소의 손상된 레코드는 건너뛰지 않고 fail-closed로 처리합니다.

## 도메인 중첩과 라우팅

두 기능의 자연어 트리거가 겹치면 안내 문구만으로 해결하지 않습니다. 다른 기능의 요청을
결정론적으로 감지할 수 있다면, 양보할 기능의 mutating 경로가 코드에서 거부하고 올바른
경로를 안내해야 합니다. 조회 경로에는 쓰기 가드를 적용하지 않습니다.

## 배포 전 점검

- 워처 파일명은 기능별로 고유한가
- 리액션 외 메시지 본문을 폴링하지 않는가
- 모든 자격증명 의존 자식에 `env=`가 있는가
- 런타임 상태가 체크아웃 밖에 저장되는가
- 실패 경로가 명확한 사유와 비정상 종료로 끝나는가
