# 장애 대응 트리

> 원인 확인 전 전체 재시작, 설정 변경, 자격증명 재발급은 금지합니다. 원시 로그와 사용자
> 본문은 티켓·저장소·공개 채널에 복사하지 않습니다.

## 첫 분기

```text
healthcheck 실패 또는 사용자 증상
├─ 특정 구성요소가 식별됨 → 해당 구성요소의 상태·의존성 진단
├─ healthcheck 정상, 기능만 이상 → UI·scheduler·권한 경계 진단
└─ 원인 불명 → 비공개 로그의 최소 정보 확인 → 마스킹된 수리 요청
```

## 증상별 원칙

| 증상 | 먼저 확인할 것 | 조치 |
|---|---|---|
| 모델 호출 실패 | 모델 게이트웨이 상태와 인증 설정 | 실패한 unit만 조건부 재시작 |
| gateway 장애 | 기반 서비스, gateway 로그, production guard | 상호의존 gateway는 함께 재시작 |
| 대시보드 장애 | 대시보드 unit과 인증 없는 요청의 거부 | 대시보드만 조건부 재시작 |
| 검색 장애 | 검색 서비스 health와 내부 의존성 | 공개 포트·키 변경 없이 원인 진단 |
| scheduler 실패 | 작업 상태·종료 코드·비공개 마스킹 로그 | 의도적 미리보기만 실행 |
| 승인·수리 요청 | ticket, sandbox, 승인, 회귀 상태 | 모든 게이트 충족 전 실행 금지 |

상세 명령과 재시작 범위는 [운영 가이드](operations.md)를, 재부팅 직후의 순서는
[재부팅 복구 절차](reboot-recovery.md)를 따릅니다.

## 기록

기록에는 구성요소 이름, 시각, 전후 active 상태, healthcheck 판정만 남깁니다. 재시도나
재시작으로 해결되지 않으면 마스킹된 수리 티켓을 만들고 소유자 검토로 에스컬레이션합니다.
