# 재부팅 후 복구 절차

이 문서는 여러 노드에 분산된 에이전트 서비스를 재부팅한 뒤의 일반적인 확인·복구 순서를
정의합니다. 재부팅 실행은 서비스 중단을 일으키므로 소유자가 정한 유지보수 창에서만 합니다.

## 사전 확인

1. 장기 실행 작업, 배포, 수리 작업이 없는지 확인합니다.
2. 재부팅 전 healthcheck와 핵심 unit 상태를 기록합니다.
3. 런타임 로그·시크릿·대시보드 자격증명을 증적에 복사하지 않습니다.

## 공통 진단

각 실행 계정에서 linger가 활성화되어 있고 user manager가 부팅 뒤 살아나는지 확인합니다.
그 다음 `is-enabled`, `is-active`, `status` 순서로 점검합니다. 실패한 unit은 원인을 확인한
뒤에만 조건부 재시작합니다.

```bash
loginctl show-user <ACCOUNT> -p Linger
systemctl --user is-enabled <UNIT>
systemctl --user is-active <UNIT>
```

원격 user-systemd 호출 형태는 [운영 가이드](operations.md)를 따릅니다.

## 권장 복구 순서

1. **기반 서비스**: 모델 게이트웨이, 데이터 저장소, 검색 인프라처럼 다른 서비스가
   의존하는 구성요소를 먼저 확인합니다.
2. **대화 gateway 집합**: 기반 서비스가 정상인 뒤, 함께 동작하도록 설계된 모든 gateway를
   확인합니다. 재시작이 필요하면 이 집합을 함께 재시작합니다.
3. **수집·UI 서비스**: 콜렉터와 대시보드를 점검합니다. 콜렉터가 워터마크 기반 backfill을
   지원하면 중단 중의 보고를 수동 재전송하지 않습니다.
4. **스케줄 작업**: scheduler의 등록 상태와 다음 실행만 확인합니다. 실제 외부효과 작업을
   임의로 강제 실행하지 않습니다.
5. **전체 판정**: 읽기 전용 healthcheck가 성공한 뒤에만 통제된 회귀 작업을 실행합니다.

## 예외 처리

ticket 인수가 필요한 one-shot 수리 unit은 boot-resident worker가 아닙니다. `inactive`가
정상일 수 있으므로 인수 없이 enable 또는 start하지 않습니다. 네트워크 준비 전에 실패할 수
있는 서비스는 재시작을 반복하는 대신 의존성·네트워크·이미지 가용성을 먼저 진단합니다.

## 기록 양식

재부팅 후에는 다음의 마스킹된 결과만 기록합니다.

| 항목 | 기록할 값 |
|---|---|
| 재부팅 시작·완료 | 시간대가 있는 시각과 노드 역할 |
| linger | 실행 계정별 yes/no |
| 핵심 unit | enabled/active 판정 |
| healthcheck | 성공 여부와 종료 코드 |
| scheduler | 등록 상태와 다음 실행 |
| one-shot unit | 의도된 대기 상태 여부 |

실제 호스트명, 주소, 원시 로그, 자격증명은 기록하지 않습니다.
