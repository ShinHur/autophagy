# DGX Spark 활용 검토

## 목적

이 문서는 DGX Spark 같은 단일 가속 노드와 두 노드를 가진 팀이 에이전트 자동화, 격리 실행, 로컬 추론을 어떻게 분리할지 판단할 때 사용하는 일반적인 기준이다. 설치별 인프라 정보나 운영 절차는 다루지 않는다.

## 핵심 판단

- 클라우드 API 중심의 에이전트 자동화는 보통 단일 노드로 충분하다. 에이전트 프로세스, 데이터베이스, 예약 작업, 임시 샌드박스의 자원 요구를 먼저 측정한다.
- 두 번째 노드는 고가용성 요구가 명확하지 않다면 기본적으로 독립된 실험·스테이징 노드로 두는 편이 안전하다.
- 두 노드 클러스터링은 대형 모델 추론, 분산 학습, 대규모 배치처럼 실제로 분산 메모리나 처리량이 필요한 경우에만 검토한다.

## 권장 역할 분리

| 역할 | 권장 워크로드 | 운영 원칙 |
|---|---|---|
| 서비스 노드 | 승인 게이트, 예약 작업, 사용자 인터페이스 | 작고 예측 가능한 상주 부하를 유지한다. |
| 실험 노드 | 스킬 샌드박스, 회귀 검증, 프로토타입 | 서비스 자격증명·상태와 분리한다. |
| 선택적 추론 노드 | 민감 자료의 로컬 추론, 배치 요약, 파인튜닝 | 별도 네트워크·모델·보존 정책을 명시한다. |

## 로컬 추론을 검토할 때

로컬 모델은 데이터 경계를 강화할 수 있지만 모델 갱신, 성능 검증, 용량 관리, 운영 책임도 함께 가져온다. 다음 질문에 모두 답할 수 있을 때만 도입한다.

1. 외부 제공자로 전송할 수 없는 데이터 분류가 있는가?
2. 목표 모델과 컨텍스트 길이가 단일 노드 메모리에 맞는가?
3. 대화 지연보다 배치 처리량이 중요한가?
4. 모델·런타임·보안 업데이트를 지속적으로 운영할 주체가 있는가?

## OpenClaw와의 관계

OpenClaw는 실험 노드에서 격리된 에이전트 환경을 검증하는 선택지가 될 수 있다. 운영 서비스와 같은 계정·비밀·저장소를 공유하지 말고, 네트워크와 실행 권한을 최소화한 상태에서 별도 검증한다.

## 도입 전 점검

- 실제 메모리·디스크·가속기 사용량을 측정한다.
- 서비스와 실험 환경의 자격증명·저장소·네트워크를 분리한다.
- 롤백 가능한 배포와 장애 시 읽기 전용 진단 절차를 마련한다.
- 실제 모델과 트래픽으로 성능·비용·민감도 경계를 검증한다.
