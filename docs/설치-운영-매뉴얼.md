# 설치·운영 매뉴얼

이 문서는 **빈 리눅스 머신에서 시작해 승인 게이트가 실제로 닫히는 배포에 도달하는 순서**를
처음부터 끝까지 한 줄로 꿴다. 저장소의 다른 문서는 각각 "왜 이런 구조인가"(`docs/design/`),
"무엇이 필요한가"(`docs/dependencies.md`), "어떤 규약을 지키는가"(`docs/guide/`)를 설명하지만,
**무엇을 어떤 순서로 실행하는가**는 어디에도 모여 있지 않았다. 그 빈칸이 이 문서다.

| 문서 | 답하는 질문 |
|---|---|
| [`README.md`](../README.md) | 이 시스템이 무엇이고 어떤 불변식을 지키는가 |
| [`docs/design/`](design/) | 왜 그렇게 설계했는가 |
| [`docs/dependencies.md`](dependencies.md) | 무엇이 필요한가 (참조표) |
| [빠른 시작](quickstart.md) | 로컬에서 아무것도 바꾸지 않고 무엇을 확인할 수 있는가 |
| **이 문서** | **어떤 순서로 무엇을 실행하는가** |

독자는 리눅스·SSH·systemd를 다뤄 봤지만 이 시스템은 처음 본다고 가정한다.

## 0. 읽는 법

### 0.1 각 단계의 형식

모든 단계는 같은 틀로 적혀 있다.

- **왜** — 이 단계가 없으면 무엇이 안 되는가. 이유 없는 명령은 따라 하다 막힌다.
- **선행 조건** — 이 단계 전에 반드시 끝나 있어야 하는 것.
- **실행 계정** — `root` / `ops` / `agent` / 작업용 워크스테이션 중 어디서 도는가.
- **명령** — 그대로 붙여 넣을 수 있는 형태.
- **무엇이 바뀌나** — 파일시스템·계정·서비스에 남는 흔적.
- **성공 신호** — 눈으로 확인할 수 있는 출력. 이것이 안 보이면 다음 단계로 가지 않는다.

### 0.2 자리표시자

실제 값은 저장소에 두지 않는다. 아래 표기가 나오면 각자의 값으로 바꾼다.

| 자리표시자 | 뜻 | 예 |
|---|---|---|
| `node-a` | 게이트웨이·스킬 배포를 돌리는 노드의 SSH 별칭 | `DEPLOY_SSH_HOST`에 넣는 값 |
| `node-b` | (선택) 검색 스택 전용 노드 | 단일 노드면 없음 |
| `192.0.2.10` | 문서 전용 예시 주소 (RFC 5737) | 실제 주소는 비공개 인벤토리에 |
| `<DISCORD_OWNER_ID>` | 소유자 Discord 사용자 ID | 17~20자리 숫자 |
| `owner@example.invalid` | 소유자 메일 주소 | — |
| `<저장소>/<이름>` | git 호스트의 저장소 슬러그 | `AUTOPHAGY_REPO_SLUG`에 넣는 값 |

### 0.3 전체 지도

| # | 단계 | 실행 계정 | 자동화 | 되돌릴 수 있나 |
|---|---|---|---|---|
| 1 | 로컬 체크아웃 검증 | 워크스테이션 | 있음 | 해당 없음(읽기만) |
| 2 | Discord 준비 | 사람(브라우저) | 없음 | 봇 삭제로 되돌림 |
| 3 | Google Workspace 준비 (조건부) | 사람(브라우저) | 없음 | 동의 철회 |
| 4 | 모델 게이트웨이 기동 (사실상 필수) | `ops` | 부분 | 컨테이너 내리기 |
| 5 | `.env` 채우기 | 워크스테이션 | 없음 | 파일 수정 |
| 6 | 노드 계정 부트스트랩 | `root` (2회 실행) | 있음 | 계정 삭제 |
| 7 | 스킬 스토어 root 헬퍼 설치 | `root` | 있음 | 마운트 해제 |
| 8 | 불변 릴리스 저장소 (권장) | `root` → `ops` | 있음 | `current` 제거 |
| 9 | 계정 비밀 파일 + interop 설정 | `root`/각 계정 | **없음(수작업)** | 파일 수정 |
| 10 | 게이트웨이 프로비저닝 | `root` (계정별) | 있음 | 유닛 중지 |
| 11 | 첫 스킬 배포 | 워크스테이션 + 소유자 ✅ | 있음 | `--remove` |
| 12 | 승인 워처 등록 | 워크스테이션 | 일부만 | cron 삭제 |

단계 6~12는 순서를 바꾸면 막힌다. 단계 2~5는 서로 독립이므로 순서를 바꿔도 된다.

## 1. 도달점 세 가지

| 도달점 | 무엇이 되는가 | 필요한 단계 | 필요한 외부 서비스 |

## 2. 준비물

### 2.1 머신

| 항목 | 요구 |
|---|---|
| OS | systemd를 쓰는 리눅스 (user systemd + `loginctl enable-linger` 필요) |
| Python | 3.12 이상 |
| 권한 | `root` 접근(계정 생성·sudoers·마운트), 그리고 `sudo -n -u agent\|peer\|ops` 무암호 전환 |
| 필수 바이너리 | `bash git ssh ssh-keygen sudo systemctl loginctl curl openssl tar sha256sum readlink flock gitleaks` |
| 조건부 바이너리 | `install mount mountpoint findmnt visudo`(스킬 스토어), `docker`+`docker compose`(모델 게이트웨이·검색) |

전체 목록과 각 항목을 무엇이 요구하는지는 [의존성 참조](dependencies.md) §1에 있다.

### 2.2 외부 서비스

| 서비스 | 필수도 | 없으면 무엇이 멈추나 |
|---|---|---|
| Discord | **필수** | 승인 메시지를 게시할 수 없다 → 모든 외부효과가 fail-closed로 멈춘다 |
| Google Workspace 호환 `gws` CLI | 전체 기능에 필수 | 일정 생성·확정, 메일 발송, Tasks 쓰기, 예산 시트 조회, 문서 발행·보관, 구매 검토, 특허 반출, 리마인더 |
| 모델 게이트웨이(LiteLLM) | 사실상 필수 | `automation/provision-agent.sh`가 게이트웨이 설정에 `http://127.0.0.1:4000/v1`을 고정으로 넣는다 |
| 검색 스택(RAG) | 선택 | `recall` 스킬이 검색 불가로 degrade하고 인제스트는 큐에 남는다. 승인 경로는 계속 동작한다 |

### 2.3 선택 구성요소 — 검색 스택

검색 스택(RAG)은 없어도 승인 경로가 그대로 도는 선택 구성요소다. 도입 전에 알아 두면
진입 판단이 쉬워지는 점을 운영 중 확인된 범위에서 적는다.

| 항목 | 내용 |
|---|---|
| 임베딩 연산 | **CPU에서 돈다.** GPU가 필수는 아니다 |
| 가용 메모리 | 실제 운영에서 사용한 기준선은 **40GiB 이상**이었다. 상한·하한이 아니라 참고선이며 설치별로 다를 수 있다 |
| 디스크 용량 | 수치가 남아 있지 않다(§15-4) |
| 임베딩 서버 패키지 설치 | 정확한 단계가 남아 있지 않다(§15-4) |

GPU가 필수가 아니라는 점 때문에 진입 장벽은 생각보다 낮다. 다만 여유 메모리가 위 기준선에
크게 못 미치면 인제스트가 느려지거나 멈출 수 있으므로, 도입 전에 메모리부터 본다.

스택이 내려가 있어도 적재분은 유실되지 않는다 — 인제스트는 큐에 쌓였다가 복구 후 다음
tick에 재시도한다(§17-4). 일반적인 하드웨어 판단 근거는
[DGX Spark 활용 검토](spark-활용-검토.md)에 있다.

## 단계 1 — 로컬 체크아웃 검증

> **왜.** 노드를 건드리기 전에, 손에 든 체크아웃이 온전한지부터 확인한다. 여기서 실패하면
> 뒤 단계의 실패 원인이 코드인지 인프라인지 구분할 수 없게 된다.

| | |
|---|---|
| 선행 조건 | Python 3.12 이상, `git`, `pytest` |
| 실행 계정 | 작업용 워크스테이션(일반 사용자) |
| 무엇이 바뀌나 | 아무것도 바뀌지 않는다. 읽기와 임시 디렉터리만 쓴다 |

```bash
git clone <저장소 URL> autophagy
cd autophagy
python3 --version                                            # 3.12 이상인지 확인
python3 -m pytest tests/unit -q
python3 tools/repo_scan.py --profile public-generic --root .
python3 tools/repo_scan.py --profile docs-claims   --root .
```

**성공 신호**

```text
SCAN-CLEAN profile=public-generic findings=0
SCAN-CLEAN profile=docs-claims findings=0
```

단위 테스트는 마지막 줄이 `passed`로 끝난다(개수·시간은 체크아웃 시점에 따라 다르다).
`pytest tests/unit`이 아니라 `python3 -m pytest tests/unit`을 쓴다 — 새 체크아웃에서 전자는
`tests` 패키지를 import하지 못할 수 있다.

이어서 [빠른 시작](quickstart.md)의 §5~§6을 따라가면, 설정이 비어 있을 때 요청이 어떻게
거부되는지를 눈으로 볼 수 있다. 그 안내는 네트워크·SSH·서비스에 접근하지 않는다.

## 단계 2 — Discord 준비 (사람이 브라우저에서)

> **왜.** 승인 게이트의 표면은 Discord다. 봇 자격증명과 채널이 없으면 승인 요청을 게시할
> 방법이 없고, 게시할 수 없으면 시스템은 아무 외부효과도 실행하지 않는다.

| | |
|---|---|
| 선행 조건 | Discord 계정, 서버 관리 권한 |
| 실행 계정 | 사람(브라우저) — 자동화하지 않는다 |
| 무엇이 바뀌나 | 저장소에는 아무것도 남지 않는다. 결과값은 단계 5에서 `.env`에 넣는다 |

### 2-1. 봇 애플리케이션 — 필수 2개, 선택 1개

두 번째 봇은 여분이 아니라 **독립된 증인**이다. 스킬 배포에는 배포를 만든 주체와 다른
주체의 attestation이 필요하고(`automation/peer_attest.py`), 그 두 번째 주체가 peer 봇이다.

| 봇 | 필수도 | 계정 | 역할 |
|---|---|---|---|
| agent 봇 | **필수** | `agent` | 소유자 대면 대화, 승인 요청 게시, 승인 리액션 폴링 |
| peer 봇 | **필수** | `peer` | 샌드박스 검토 결과를 자기 신원으로 증언 |
| 수집 봇 | **선택** | 수집 전용 계정 | 보고 허브를 쓸 때만. 읽기만 하고 아무것도 쓰지 않는다 |

세 번째 봇은 [보고 허브](guide/report-hub.md)를 켜지 않으면 만들 필요가 없다. 운영 중
확인된 형태도 "필수 2개 + 보고 허브를 쓸 때만 세 번째"였다.

각 봇마다 별도 애플리케이션·별도 토큰을 만든다. 메시지 본문을 읽어야 하면
**Message Content Intent**를 켠다. `Administrator`·역할 관리·서버 관리 권한은 주지 않는다.

### 2-2. 초대할 때 고르는 OAuth scope와 권한

초대 URL의 형태는 아래와 같다.

```text
https://discord.com/api/oauth2/authorize?client_id=<애플리케이션 ID>&scope=bot%20applications.commands&permissions=<정수>
```

| 항목 | 값 |
|---|---|
| OAuth scope | `bot` + `applications.commands` — 두 개 모두 |
| agent 봇 / peer 봇 권한 | `View Channels`, `Send Messages`, `Read Message History`, `Create Public Threads`, `Send Messages in Threads`, `Add Reactions`, `Attach Files` |
| 수집 봇 권한 | `View Channels`, `Read Message History` **만** |

수집 봇에 전송 권한을 주지 않는 것이 최소 권한 원칙의 가장 알기 쉬운 실례다. 그 봇은 읽기만
하면 되고, 쓰기 권한이 아예 없으면 오작동해도 채널에 아무것도 남기지 못한다.

`<정수>`는 손으로 계산하지 않는다. Discord 개발자 포털의 URL 생성기에서 위 체크박스를
고르면 자동으로 채워진다. **정확한 정수값은 저장소에도 운영 기록에도 남아 있지 않다**(§15-2).

애플리케이션 ID는 초대 URL에만 쓰이고 런타임이 읽지 않는다. 그래서 어떤 환경 변수에도
넣을 필요가 없다.

### 2-3. 서버와 채널

| 서버 | 채널 | 용도 |
|---|---|---|
| 공유 서버 | `#team` | 사람과 봇의 일반 논의 |
| 공유 서버 | `#agents-log` | 마스킹된 구조화 상태 보고 |
| 공유 서버 | `#agent-coordination` | 봇 간 조율 봉투 |
| 개인 서버 | `#approvals` | 스킬 배포·attestation·발행·managed 활성화 승인 |
| 소유자 DM | — | 메일·일정·예산·조율·위키·문서보관·특허반출·수리·노트쓰기 승인 |

공유 서버에 `#approvals`를 만들지 않는다. 채널 이름으로 탐색하는 구현이 있어서, 봇의 시야에
`approvals`라는 이름의 채널이 둘 이상이면 fail-closed로 멈춘다
(`automation/interop/approval_directory.py`).

### 2-4. 승인 표면이 갈리는 규칙

어떤 승인이 `#approvals`로 가고 어떤 승인이 DM으로 가는지는 문서가 아니라 코드가 정한다 —
`automation/interop/approval_surface.py`.

| 승인 종류(코드의 `ApprovalKind`) | 표면 |
|---|---|
| `SKILL_DEPLOY`, `SKILL_ATTEST`, `SKILL_PUBLISH`, `MANAGED_ACTIVATE` | 개인 서버 `#approvals` |
| `MAIL_REPLY`, `MAIL_COMPOSE`, `BUDGET_MAIL`, `DRIVE_ARCHIVE`, `PATENT_EXPORT`, `REPAIR`, `CALENDAR`, `COORDINATION`, `WIKI`, `OBSIDIAN_WRITE` | 소유자 DM |

공급망 승인만 채널로 가는 이유는 단순하다: 2차 주체인 peer 봇이 같은 메시지를 봐야 한다.
DM은 소유자와 한 봇 사이의 공간이라 그것이 불가능하다.

### 2-5. 모아 둘 값

| 값 | 어디서 얻나 |
|---|---|
| `DISCORD_OWNER_ID` | 개발자 모드를 켜고 소유자 계정에서 Copy User ID |
| `DISCORD_GUILD_ID` | 서버에서 Copy Server ID |
| `DISCORD_OWNER_DM_CHANNEL_ID` | 소유자 DM을 연 뒤 API 응답의 채널 ID |
| `DISCORD_APPROVALS_CHANNEL_ID` | `#approvals`에서 Copy Channel ID |
| `DISCORD_BOT_USER_ID_AGENT` / `_PEER` | 설치된 각 봇 계정에서 Copy User ID |
| 봇 토큰 2개 | 각 애플리케이션에서 1회만 복사 |

**봇은 둘인데 토큰 변수는 `DISCORD_BOT_TOKEN` 하나다 — 이것은 모순이 아니라 정상 설계다.**
변수 **이름은 같고 파일이 다르다.** 각 봇은 자기 리눅스 계정으로 돌고, 계정마다 자기
`~/.env.secrets`를 가지며, 그 안에 각각 자기 봇의 `DISCORD_BOT_TOKEN`이 들어간다. 게이트웨이
유닛은 그 계정의 파일만 읽으므로 두 토큰이 섞이지 않는다 — **계정 격리가 곧 토큰 격리다.**
두 계정의 파일에 같은 토큰을 넣으면 attestation의 독립성이 사라진다(단계 9).

남은 공백은 하나뿐이다. 초대 URL의 permission 정수값은 어디에도 보존돼 있지 않다(§15-2).
위 §2-2의 체크박스를 포털에서 골라 생성한다.

상세: [Discord 서버와 봇 설정 가이드](guide/w0-5-discord-setup.md),
[Discord 협업 서버 아키텍처](guide/discord-server-architecture.md).

## 단계 3 — Google Workspace 준비 (조건부)

> **왜.** 일정·메일·시트·드라이브를 건드리는 스킬은 외부 `gws` CLI를 통해 동작한다. 채팅과
> 승인 루프만 쓸 생각이면 이 단계를 건너뛰어도 나머지는 전부 동작한다.

| | |
|---|---|
| 선행 조건 | Google Cloud 프로젝트, 소유자 계정의 브라우저 접근 |
| 실행 계정 | 사람(브라우저) — **헤드리스에서 로그인 시도 금지** |
| 무엇이 바뀌나 | 자격증명이 비공개 저장소에 생긴다. 저장소에는 아무것도 남지 않는다 |

### 3-1. OAuth 클라이언트와 scope

| 항목 | 값 |
|---|---|
| 클라이언트 타입 | **Desktop** |
| 이미 있는 경우 | 새로 만들지 말고 재사용한다 |
| 프로젝트 ID | `.env`의 `GCP_PROJECT_ID` |

동의할 scope는 **정확히 10개**다(운영 중 확인된 집합).

```text
openid
email
profile
userinfo.email
userinfo.profile
calendar
drive
spreadsheets
gmail.send
tasks
```

> **동의 화면에서 "모두 선택"을 누르지 않는다.** 위 10개만 승인한다. 쓰지 않는 scope를 미리
> 받아 두면, 자격증명이 새는 사고가 났을 때 피해 범위가 그만큼 넓어진다. 읽기 전용 기능에
> 쓰기 scope를 얹지 않는 것도 같은 이유다.

scope를 바꾸면 재동의가 필요하다. 나중에 기능을 하나 더 켤 때 브라우저 앞에 한 번 더
앉아야 한다는 뜻이므로 미리 계산에 넣는다.

### 3-2. `gws` CLI 설치

운영 중 확인된 방식은 Google Workspace CLI의 **공식 릴리스 아카이브**를 받아 설치하는
것이다. 저장소가 이 실행 파일을 담고 있지는 않다.

| 순서 | 하는 일 |
|---|---|
| ① | 노드 아키텍처에 맞는 릴리스 아카이브를 고른다 — 먼저 `uname -m`으로 확인한다 |
| ② | **sha256 체크섬을 검증한다.** 이 단계를 건너뛰지 않는다 |
| ③ | 실행 파일을 `~/.local/bin/gws`에 배치한다 |

### 3-3. 로그인은 워크스테이션에서만

로그인은 **소유자의 로컬 워크스테이션에서 Desktop OAuth로만** 수행한다.
**헤드리스 노드에서 브라우저 로그인을 시도하지 않는다** — 그 시도는 완료되지 않고 중간
상태의 잔여 세션만 남긴다.

인증이 끝나면 `~/.config/gws/` 아래에 산출물 3종이 생긴다.

| 산출물 | 성격 |
|---|---|
| 암호화된 자격증명 파일 | 계정 자격증명 |
| 암호화 키 파일 | 위 파일을 여는 키 |
| OAuth 클라이언트 시크릿 파일 | 클라이언트 등록 정보 |

토큰 캐시는 지워도 된다 — 다음 실행에서 다시 만들어진다. 위 3종은 그렇지 않다.

**워크스테이션에서 인증한 뒤 그 산출물을 노드로 옮기는 것이 실제 흐름이다.** 옮길 때는
일회성 보호 전송 경로를 쓰고, 옮긴 뒤 워크스테이션 쪽 staging 사본을 지우며, 노드에서는
소유권과 mode(`0700`/`0600`)만 확인한다.

### 3-4. 검증과 경로 고정

1. 검증은 **읽기 전용 호출로만** 한다. 발송·업로드·일정 변경 같은 검증은 반드시 기존 승인
   게이트를 거치는 별도 작업으로 수행한다.
2. `gws` 실행 파일 경로와 실행 계정을 고정한다. cron에서는 `PATH`와 자격증명 위치를 명시한다.

각 스킬은 `gws` 실행 파일을 자기 전용 환경 변수로 덮어쓸 수 있다.

| 스킬/구성요소 | 환경 변수 |
|---|---|
| 예산 | `BUDGET_GWS_BIN` |
| 일정 | `CALENDAR_GWS_BIN` |
| 문서 보관 | `DRIVE_ARCHIVE_GWS_BIN`, `DRIVE_GWS_BIN`, `DRIVE_PUBLISH_GWS_BIN` |
| 특허 반출 | `PATENT_GWS_BIN` |
| 구매 검토 | `PROCURE_GWS_BIN` |
| 리마인더 | `REMINDER_GWS_BIN` |
| 할 일 | `TODO_GWS_BIN` |
| 공통 폴백 | `GWS_BIN` |

미설정 시 `PATH`에서 찾는다.

상세: [Google Workspace CLI OAuth 설정 가이드](guide/w0-6-gws-oauth-setup.md).

## 단계 4 — 모델 게이트웨이 (사실상 필수)

> **왜.** `automation/provision-agent.sh`는 게이트웨이 설정에 `http://127.0.0.1:4000/v1`과
> 모델 `glm-main`을 **고정 값으로** 써 넣는다. 게이트웨이 계정이 대화를 하려면 그 주소에서
> 무언가가 응답해야 한다. 또한 민감도 차단기가 이 계층에 있어서, 없으면 민감 요청을 막을
> 지점 자체가 사라진다.

| | |
|---|---|
| 선행 조건 | 모델 제공자 API 키, `docker` + `docker compose`, `ops`가 docker 그룹 |
| 실행 계정 | `ops` |
| 무엇이 바뀌나 | `127.0.0.1:4000`에 컨테이너가 뜨고, 가상 키가 발급된다 |

**docker 그룹 preflight를 먼저 통과해야 한다.** root가 `ops`를 docker 그룹에 넣고, `ops`의
새 세션에서 아래가 성공해야 다음으로 간다. 실패하면 막힌 것으로 간주하고 멈춘다 —
런북은 `sudo docker`·rootless·`/etc/group` 직접 수정 같은 우회를 의도적으로 제공하지 않는다.

```bash
id -nG | tr ' ' '\n' | grep -qx docker && docker ps >/dev/null
```

번들과 절차는 `configs/litellm-staging/DEPLOY.md`에 있다. 요점만 옮기면:

| 항목 | 값 / 위치 |
|---|---|
| 바인딩 | `127.0.0.1:4000` (`configs/litellm-staging/docker-compose.yml`) |
| 제공자 API 키 | 모델 제공자를 호출할 자격증명 |
| 데이터베이스 접속 문자열 | 사용량·가상 키 원장의 저장소 |
| `POSTGRES_PASSWORD` | 그 데이터베이스의 비밀번호 |
| `LITELLM_MASTER_KEY` | 마스터 키 — `sk-` 접두가 필요하다 |
| `LITELLM_SALT_KEY` | **솔트 키.** 가상 키를 만들고 보관할 때 쓰는 필수 보안값 |
| `WEBHOOK_URL` | 예산 알림 이벤트를 내보낼 목적지 |
| 예산 알림 전송 | 봇 토큰과 소유자 ID |
| 예산 상하한 | `LITELLM_SOFT_BUDGET`(소프트 경보), `LITELLM_HARD_BUDGET`(하드 상한) |
| 키 상한·주기 | `configs/litellm-staging/config.yaml`의 `max_budget`과 `budget_duration: "30d"` |
| 예산 강제 | `general_settings.fail_closed_budget_enforcement: true` |
| 민감도 차단기 | `configs/litellm-staging/custom_callbacks.py` |

위 집합은 운영 중 확인된 것이다. **솔트 키가 없으면 스택 자체가 뜨지 않는다** — 마스터 키만
채우고 넘어가기 쉬운 자리인데, 그러면 compose가 기동을 거부한다.

민감도 차단기는 `glm-main` 요청에 patent-sensitive 태그나 센티널이 섞이면 **HTTP 403**으로
막는다. 이 계층이 없으면 민감 요청이 외부 제공자로 그대로 나간다.

계정별 가상 키를 발급해 각 계정의 `~/.env.secrets`에 넣는다 — `agent`는
`LITELLM_AGENT_KEY`, `peer`는 `LITELLM_PEER_KEY`다(단계 9). 키 이름은 계정명을 대문자로
바꿔 만든 `LITELLM_<계정>_KEY` 규칙이다.

**`LITELLM_SALT_KEY`와 `WEBHOOK_URL`은 루트 `.env.example`에 없다.** 이 둘은 compose 옆의
로컬 환경 파일에 따로 채운다. 루트 `.env`와 병합하지 않는다 — 검색 스택 설정
(`configs/rag/env.example`)이 분리돼 있는 것과 같은 이유다.

상세: [모델 제공자 자격증명 설정 가이드](guide/w0-6-provider-keys-setup.md).

## 단계 5 — `.env` 채우기

> **왜.** 이 시스템에는 기본값이 없다. 비어 있는 값은 다른 값으로 대체되지 않고 `ConfigError`로
> 중단한다. 이것이 중심 안전 속성이므로, 채우지 않은 채로 다음 단계에 가면 나중에 무엇이
> 비어 있었는지 추적하기 어려운 지점에서 멈추게 된다.

| | |
|---|---|
| 선행 조건 | 단계 2 완료(단계 3·4는 해당 기능을 쓸 때만) |
| 실행 계정 | 워크스테이션 |
| 무엇이 바뀌나 | 추적되지 않는 개인 설정 파일 하나가 생긴다 |

```bash
cp .env.example .env
$EDITOR .env
chmod 600 .env
```

지금 반드시 채워야 하는 최소 집합은 아래다. 나머지 약 55개 키는 해당 기능을 켤 때 채운다.

| 그룹 | 키 | 형식 검증 |
|---|---|---|
| 채팅 신원 | `DISCORD_OWNER_ID`, `DISCORD_GUILD_ID`, `DISCORD_OWNER_DM_CHANNEL_ID`, `DISCORD_APPROVALS_CHANNEL_ID`, `DISCORD_BOT_USER_ID_AGENT`, `DISCORD_BOT_USER_ID_PEER` | 17~20자리 숫자 |
| 채팅 자격증명 | `DISCORD_BOT_TOKEN` | (추적 파일에 두지 않는다) |
| 배포 대상 | `DEPLOY_SSH_HOST` | 호스트명 형식 |
| 배포 루트 | `AUTOPHAGY_DEPLOY_ROOT`, `AUTOPHAGY_PRIVATE_ROOT`, `AUTOPHAGY_SKILLS_ROOT` | 절대 경로 |
| 저장소 | `AUTOPHAGY_REPO_SLUG` | `<저장소>/<이름>` |
| 소유자 | `OWNER_EMAIL`, `ORGANIZATION_LABEL` | 메일 형식 / 자유 |

검증 규칙의 정본은 `automation/config_env.py`다. 그 파일이 **직접 아는** 키는 15개뿐이고,
나머지는 각 구성요소가 자기 자리에서 읽는다.

`AUTOPHAGY_SKILLS_ROOT`는 단계 7의 스킬 스토어와 **반드시 같은 자리를 가리켜야 한다** —
`automation/deploy-skill.sh`는 이 값의 상위 디렉터리를 스토어 루트로 계산하고,
`automation/provision-readonly-skills.sh`는 스토어 경로를 스크립트 안에 고정으로 들고
있다(§15-6).

키 하나하나의 용도와 필수도는 [의존성 참조](dependencies.md) §3의 표에 있다.

## 단계 6 — 노드 계정 부트스트랩 (2회 실행)

> **왜.** 이 시스템은 한 계정 안에서 돌지 않는다. 배포를 만든 주체와 검증한 주체가 같으면
> 검증이 아니기 때문이다. 이 스크립트가 그 계정 분리와 그에 딸린 권한·디렉터리·훅을 만든다.

| | |
|---|---|
| 선행 조건 | 단계 5의 `AUTOPHAGY_REPO_SLUG`·`AUTOPHAGY_DEPLOY_ROOT`·`AUTOPHAGY_PRIVATE_ROOT`, `root` 접근, `git curl tar ssh ssh-keygen sudo` |
| 실행 계정 | `root` (대상 노드에서) |
| 무엇이 바뀌나 | 계정 3개, linger, 홈 `700`, 빈 `~/.env.secrets` `600`, `autophagy` 그룹, agent 홈 골격, 비공개 루트 `700`, 배포 루트 `2750`(setgid), `gitleaks` 8.30.1, 계정별 git 설정, `ops` 배포 키, 배포 체크아웃, 커밋 거부 훅 |

역할 인자는 두 가지다.

| 역할 | 만드는 계정 | 요구하는 환경 변수 | 실행 횟수 |
|---|---|---|---|
| `production` | `agent`, `peer`, `ops` | 세 개 모두 | **2회** |
| `rag` | `ops` | 없음 | 1회 |

### 6-1. 1회차

```bash
sudo env AUTOPHAGY_REPO_SLUG=... AUTOPHAGY_DEPLOY_ROOT=... AUTOPHAGY_PRIVATE_ROOT=... \
  bash automation/bootstrap-accounts.sh production
```

스크립트는 8단계를 진행하다가 배포 키 직전에서 **일부러 멈춘다.**

**성공 신호(1회차)** — 배너가 뜨고 exit 0으로 끝난다.

```text
===== PHASE 1 COMPLETE — HUMAN ACTION REQUIRED (deploy key not registered yet) =====
```

배너 안에 `ops`의 공개키 한 줄과 등록 페이지 URL이 함께 출력된다.

### 6-2. 사람의 작업

출력된 URL에서 그 공개키를 **읽기 전용 Deploy Key**로 등록한다. 배너가 명시하듯
**`Allow write access`는 체크하지 않는다.** 배포 체크아웃은 단방향 거울이므로 쓰기 권한을
주면 그 방향이 깨진다.

스크립트가 이 등록을 대신하지 않는 이유는 저장소 관리자 권한이 필요하고 `ops` 계정에
인증된 `gh`가 없기 때문이다.

### 6-3. 2회차

같은 호스트에서 같은 명령을 다시 실행한다. 스크립트는 완전 멱등이라 몇 번을 돌려도 안전하고,
비밀 파일은 절대 잘라내지 않는다.

**성공 신호(2회차)**

```text
[bootstrap] GitHub deploy-key auth OK (ops)
[bootstrap] DONE (role=production) — all phases complete
```

### 6-4. 여기서 생긴 규칙

배포 체크아웃(`AUTOPHAGY_DEPLOY_ROOT`)에는 **모든 커밋을 무조건 거부하는** pre-commit 훅이
설치된다. 허용되는 쓰기는 `git fetch`와 `git pull --ff-only`뿐이다. 조건부 거부가 아니라
무조건 거부인 이유는, 예외를 아는 사람에게만 통하는 규칙은 사고를 내는 쪽에 통하지 않기
때문이다.

**흔한 실패**

| 증상 | 원인 | 조치 |
|---|---|---|
| `AUTOPHAGY_REPO_SLUG is required — see .env.example` | 환경 변수 미전달 | `sudo env VAR=... bash ...` 형태로 전달 |
| `must run as root: sudo bash bootstrap-accounts.sh <role>` | root 아님 | `sudo`로 실행 |
| `linger verification failed for '<user>'` | `loginctl` 부재/실패 | systemd·`loginctl` 확인 |
| `$DEPLOY_DIR is non-empty but not a git repo` | 배포 루트에 잔여물 | 손으로 확인 후 정리, 자동 삭제하지 않는다 |

## 단계 7 — 스킬 스토어 root 헬퍼 설치

> **왜.** 스킬 마운트는 `root`만 할 수 있고, 그 일은 `agent`가 아니라 root 소유 헬퍼가
> 수행한다. 이 헬퍼와 sudoers 조각이 없으면 단계 11의 마지막 MOUNT가 실패한다 — 앞의 세
> 단계(샌드박스·검토·승인)를 다 통과하고 마지막에 막히는 것이 가장 아까운 실패다.

| | |
|---|---|
| 선행 조건 | 단계 6 완료(`agent` 계정 존재), `install python3 tar mount mountpoint findmnt visudo systemctl` |
| 실행 계정 | `root` (노드에서) |
| 무엇이 바뀌나 | 스킬 스토어 루트와 `live`, root 헬퍼 `/usr/local/libexec/autophagy-install-skill`, sudoers 조각, agent의 스킬 디렉터리가 읽기 전용 bind-mount로 대체 |

```bash
sudo bash automation/provision-readonly-skills.sh
```

스크립트는 저장소의 각 스킬을 헬퍼로 한 번씩 설치한 뒤, agent의 스킬 디렉터리를
`bind,ro,nosuid,nodev`로 마운트한다. 기존 agent 소유 디렉터리가 있으면 **지우지 않고**
타임스탬프를 붙여 백업한다.

**성공 신호**

```text
[provision-readonly-skills] READY source=... target=... options=... hub_options=...
```

**주의.** 이 스크립트는 스토어 경로와 agent의 마운트 지점을 스크립트 안에 고정으로 들고
있다. `.env`의 `AUTOPHAGY_SKILLS_ROOT`가 그 스토어의 `live` 디렉터리를 가리키지 않으면,
배포는 헬퍼가 쓴 곳과 다른 곳을 읽게 된다(§15-6).

## 단계 8 — 불변 릴리스 저장소 (권장, 생략 가능)

> **왜.** 이 단계를 건너뛰면 배포 체크아웃 자체가 프로덕션 런타임이 된다. 즉 누군가 그
> 체크아웃을 건드리는 순간 돌고 있는 코드가 바뀐다. 릴리스를 쓰면 체크아웃은 관측소로
> 내려가고, 실제 런타임은 SHA로 고정된 읽기 전용 스냅샷이 된다.

| | |
|---|---|
| 선행 조건 | 단계 6 완료, `install python3 visudo` |
| 실행 계정 | `root` → 그다음 `ops` |
| 무엇이 바뀌나 | 릴리스 저장 루트(0755 root:root), root 헬퍼, sudoers 조각, 그리고 `current` 심링크 |

### 8-1. 저장소 마련 (root, 1회)

```bash
sudo bash automation/provision-release-store.sh
```

**성공 신호**

```text
[provision-release-store] READY store_root=... helper=... sudoers=...
```

### 8-2. 수렴 (ops, 반복)

`origin/main`의 SHA로 스냅샷을 떠서 릴리스로 설치하고 `current`를 원자적으로 교체한다.

```bash
sudo -n -u ops -H bash automation/converge-release-runtime.sh
```

**성공 신호**

```text
[converge-release] converged: current -> <sha>
```

`automation/release_store.py`가 실제 설치·검증을 수행하며, 각각 아래를 출력한다.

```text
RELEASE-STORE-OK installed=<release> current-><sha>
RELEASE-STORE-OK current==<sha>
```

### 8-3. 런타임 루트가 결정되는 순서

`automation/runtime_root.py`(그리고 셸 쪽 `automation/runtime_root.sh`)가 이 순서로 정한다.

| 우선순위 | 근거 |
|---|---|
| 1 | 환경 변수 `AUTOPHAGY_RUNTIME_ROOT` |
| 2 | 릴리스 `current` 심링크 — **존재할 때만** |
| 3 | 배포 체크아웃(미러) |

> **함정.** 2단계의 판정은 `Path.exists()`다. 심링크가 **깨져 있으면** `exists()`가 거짓이므로
> 해석기는 조용히 3단계(미러)로 내려간다. 즉 **손상된 릴리스가 "릴리스 없음"과 구분되지
> 않는다.** 릴리스를 쓰기로 했다면, 배포 뒤에 `current`가 실제로 무엇을 가리키는지 확인하는
> 습관을 들인다. `automation/land.sh`는 이 경우를 별도로 취급해, 깨진 `current`를 부재가
> 아니라 손상으로 보고 랜딩을 거부한다.

### 8-4. 이후의 반영 절차

코드를 노드에 반영하는 정상 경로는 하나다.

```bash
bash automation/land.sh
```

이 명령은 개발 체크아웃이 dirty하거나 기준보다 뒤처져 있으면 차단하고, push한 뒤 노드의
런타임을 그 SHA로 수렴시킨 다음 사후조건을 검증한다.

**성공 신호(두 형태 중 하나)**

```text
landed: origin/main=<sha> runtime=release@<sha> mirror=<verdict> abi=<ok|warn>
landed: origin/main=<sha> runtime=mirror@<sha> (no release installed) abi=<ok|warn>
```

## 단계 9 — 계정 비밀 파일과 interop 설정 (수작업)

> **왜.** 단계 6은 `~/.env.secrets`를 **빈 파일로** 만들어 둔다. 채우는 것은 사람 몫이다.
> 그리고 승인 흐름 전체가 읽는 `~/.hermes/interop/config.json`은 **저장소의 어떤 스크립트도
> 만들어 주지 않는다** — 이 파일이 없으면 단계 10 이후가 전부 fail-closed로 멈춘다.

| | |
|---|---|
| 선행 조건 | 단계 2(토큰), 단계 4(가상 키), 단계 6(계정) |
| 실행 계정 | 각 계정(`agent`, `peer`) 또는 `root` |
| 무엇이 바뀌나 | 체크아웃 밖의 계정 홈에만 파일이 생긴다 |

### 9-1. `~/.env.secrets`

`agent`와 `peer` 각각에 대해, 소유자가 그 계정이고 모드가 `0600`이어야 한다. 단계 10의
`automation/provision-agent.sh`가 이 두 가지를 실제로 검사하고 틀리면 즉시 중단한다.

| 계정 | 반드시 비어 있지 않아야 하는 키 |
|---|---|
| `agent` | `DISCORD_BOT_TOKEN`(agent 봇), `LITELLM_AGENT_KEY` |
| `peer` | `DISCORD_BOT_TOKEN`(peer 봇), `LITELLM_PEER_KEY` |

워처(cron)도 이 파일을 자기 손으로 읽는다 — no-agent cron은 환경에 비밀을 넣어 주지 않기
때문이다. 그래서 워처는 시작하자마자 `~/.env.secrets`를 스스로 로드하고, 자식 프로세스에는
필요한 값만 명시 전달한다(상속에 기대지 않는다).

### 9-2. `~/.hermes/interop/config.json`

각 게이트웨이 계정의 홈에 직접 만든다. 모드는 `0600`을 권한다.

**운영 중 확인된 실제 형태**는 기본 4개 + 선택 1개다. 승인 채널을 정하는 자리가 여기뿐이므로,
`.env`를 아무리 채워도 이 파일이 비어 있으면 표면이 정해지지 않는다.

| 키 | 필수도 | 값 |
|---|---|---|
| `agent_id` | 기본 | 이 봇의 공개 agent_id |
| `agents_log_channel_id` | 기본 | 공유 서버 `#agents-log` 채널 ID |
| `interop_channel_id` | 기본 | 공유 서버 `#agent-coordination` 채널 ID |
| `owner_id` | 기본 | 소유자 Discord 사용자 ID |
| `personal_approvals_channel_id` | 선택 | 개인 서버 `#approvals`를 명시할 때만 |

```json
{
  "agent_id": "<이 봇의 공개 agent_id>",
  "agents_log_channel_id": "<공유 서버 #agents-log 채널 ID>",
  "interop_channel_id": "<공유 서버 #agent-coordination 채널 ID>",
  "owner_id": "<DISCORD_OWNER_ID>",
  "personal_approvals_channel_id": "<개인 서버 #approvals 채널 ID>"
}
```

각 키를 누가 읽고, 없으면 어떻게 되는지는 아래와 같다. 배포 계열은
`deploy_approvals_channel_id`를 추가로 읽는다.

| 키 | 누가 읽나 | 없으면 |
|---|---|---|
| `owner_id` | 거의 모든 승인 게이트(`automation/skill_gate.py`, `skills/wiki/scripts/wiki_gate.py` 등) | `FATAL: owner_id missing from interop config` |
| `personal_approvals_channel_id` | `automation/interop/approval_directory.py` | 캐시 → 길드 스캔 순으로 폴백 |
| `deploy_approvals_channel_id` | `automation/deploy-skill.sh`, `automation/skill_gate_surface.py` | 빈 값으로 넘기고 peer 쪽 길드 스캔 폴백 |
| `agent_id` | 인터롭 보고·조율 | 해당 기능만 멈춤 |
| `agents_log_channel_id` | 구조화 상태 보고 | 해당 기능만 멈춤 |
| `interop_channel_id` | 봇 간 조율 봉투 | 해당 기능만 멈춤 |

**승인 채널 해석 순서**는 세 단계다.

| 순위 | 근거 |
|---|---|
| 1 | `personal_approvals_channel_id` |
| 2 | 디스크 캐시 |
| 3 | 길드 스캔 — 이름으로 유일한 승인 채널을 찾는다 |

3순위 때문에 봇 시야에 `approvals`라는 이름의 채널이 둘 이상이면 fail-closed로 멈춘다.
1순위를 명시해 두면 그 문제 자체가 생기지 않는다.

> **가장 흔한 착각.** `.env`의 `DISCORD_APPROVALS_CHANNEL_ID`와
> `DISCORD_OWNER_DM_CHANNEL_ID`를 채웠다고 승인 표면이 정해지지 않는다. 실제 해석기는 그
> 변수들을 **읽지 않는다.** 대신 채워야 하는 것은 위 JSON의
> `personal_approvals_channel_id`이고, 배포 계열은 `deploy_approvals_channel_id`다.

**흐름별 환경 변수 override는 제거된 설계다.** 채널마다 다른 변수를 두지 않으며, 새 승인
표면이 필요해도 새 변수를 만들지 않는다 — 차이는 저장 레코드의 채널 바인딩으로만 표현한다.
그래서 "이 흐름은 어떤 변수로 채널을 바꾸는가"라는 질문은 성립하지 않는다.

경로는 `INTEROP_CONFIG` 환경 변수로 바꿀 수 있다.

## 단계 10 — 게이트웨이 프로비저닝

> **왜.** 소유자와 대화하고 승인 메시지를 게시하는 프로세스가 여기서 생긴다. 이 단계 전까지
> 시스템에는 "말하는 입"이 없다.

| | |
|---|---|
| 선행 조건 | 단계 6·9 완료, `sudo -n -u <계정>` 가능, linger 활성, 단계 4의 게이트웨이가 응답 |
| 실행 계정 | `root`(또는 `sudo -n -u <계정>` 권한을 가진 계정) |
| 무엇이 바뀌나 | 외부 Hermes 설치, `~/.hermes/config.yaml`, systemd user drop-in, `hermes-gateway.service` 기동 |

```bash
sudo bash automation/provision-agent.sh agent
sudo bash automation/provision-agent.sh peer
```

**게이트웨이 재시동이 필요해지면 agent와 peer를 함께 재시동한다.** 한쪽만 되살리면
attestation 경로가 반쪽이 된다.

### 10-1. 먼저 검사하고, 실패하면 아무것도 하지 않는다

| 검사 | 실패 메시지(발췌) |
|---|---|
| 계정 존재 | `account '<ACCOUNT>' does not exist ...` |
| 무암호 전환 | `cannot run commands as '<ACCOUNT>' without a password; ...` |
| 비밀 파일 존재 | `required secrets file is missing: .../.env.secrets ...` |
| 소유자·모드 | `... must be owned by '<ACCOUNT>' and mode 600 (found owner=... mode=...)` |
| 토큰 | `... is missing a non-empty DISCORD_BOT_TOKEN entry` |
| 모델 키 | `... is missing a non-empty LITELLM_<SUFFIX>_KEY entry` |
| linger | `linger is not enabled for '<ACCOUNT>'` |

### 10-2. 무엇을 하나

1. 외부 Hermes 공식 설치기를 `curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash`로
   실행한다. **이 설치 URL 자체에는 버전 핀이 없다** — 그래서 설치 직후 실제 버전을 기록해
   두고, 재구축할 때 같은 버전인지 대조하는 운영 습관이 필요하다(§15-1).
2. `~/.hermes/config.yaml`과 `~/.config/systemd/user/hermes-gateway.service.d/10-env-secrets.conf`를
   **없을 때만** 만든다. 이미 있으면 내용을 비교해 `already matches — skipping` 또는
   `already set — preserving (only-if-unset)`으로 보존한다.
3. `hermes gateway install --force --start-now`로 유닛을 설치·기동한다.

`agent` 계정에만 fallback provider 블록이 추가된다. `peer`에는 없다.

### 10-3. 성공 신호

```text
[provision-agent] verification: hermes-gateway.service is active for '<ACCOUNT>'
[provision-agent] DONE: '<ACCOUNT>' is provisioned; no OAuth or user DM test was attempted
```

마지막 문구가 말하듯, 이 단계는 **OAuth도 DM도 시험하지 않는다.** 그 확인은 단계 11과
§13에서 한다.

직접 확인하려면:

```bash
sudo -n -u agent env XDG_RUNTIME_DIR=/run/user/$(id -u agent) \
  systemctl --user is-active hermes-gateway.service
```

출력이 `active`여야 한다.

### 10-4. `~/.hermes/config.yaml`이 담는 것

운영 중 확인된 형태는 아래 항목으로 이루어진다.

| 항목 | 값의 성격 |
|---|---|
| 주 제공자 | 로컬 모델 게이트웨이 (`custom:litellm` 형태) |
| 주 모델 | 게이트웨이에 등록한 모델 별칭 |
| `base_url` | 로컬 게이트웨이의 `/v1` |
| 키 | 값이 아니라 **환경 변수 이름**(`key_env`) |
| API 모드 | chat completions |
| 폴백 | 폴백 제공자와 모델 (`agent`에만 있고 `peer`에는 없다) |

> **키를 파일에 직접 쓰지 않고 환경 변수 이름만 적는다.** 그래서 이 설정 파일이 유출돼도
> 키는 새지 않는다. 실제 값은 systemd user drop-in이 읽는 `~/.env.secrets` 한 곳에만 있다.

drop-in은 그 계정의 `~/.env.secrets`를 `EnvironmentFile=`로 읽는다. 즉 비밀은 유닛 파일에도
설정 파일에도 없고 그 파일 하나에만 있다 — 유출 시 회수해야 할 자리가 하나로 줄어든다.

**주의(§15-1).** Hermes 게이트웨이 본체는 이 저장소에 없다. 위 URL을 호출할 뿐이며 버전
고정도 체크섬 검증도 없다. 설치 직후 버전을 기록해 두는 습관이 그 공백을 메운다.

상세: [게이트웨이 계정 프로비저닝](guide/provision-agent-script.md).

## 단계 11 — 첫 스킬 배포

> **왜.** 여기서 처음으로 4단계 게이트가 전부 돈다 — 샌드박스, 검토, 승인+attestation,
> 마운트. 이것이 통과하면 계정 분리·root 헬퍼·승인 표면·peer 신원이 모두 실제로 맞물려
> 있다는 뜻이다.

첫 대상은 `hello-autophagy`를 권한다. 네트워크 호출도 파일 쓰기도 시크릿 읽기도 없는
결정론적 데모 스킬이라, 실패하면 원인이 파이프라인 쪽이라고 단정할 수 있다.

| | |
|---|---|
| 선행 조건 | 단계 6·7·9·10 완료, 배포 대상 코드가 `origin/main`에 있을 것 |
| 실행 계정 | 워크스테이션(내부적으로 `agent`/`peer`/`ops`/`root`로 갈라진다) |
| 무엇이 바뀌나 | 승인 메시지 1건, 스킬 스토어에 릴리스 1건, `live` 심링크 갱신 |

필요한 환경 변수는 `DEPLOY_SSH_HOST`, `AUTOPHAGY_DEPLOY_ROOT`, `AUTOPHAGY_SKILLS_ROOT`이고,
`agent`·`peer`·`ops`에 대한 무암호 `sudo -n -u`가 있어야 한다.

### 11-1. 샌드박스만 먼저

```bash
bash automation/deploy-skill.sh hello-autophagy --sandbox-only
```

샌드박스는 스킬을 **peer** 인스턴스에 복사한 뒤, `env -i`로 환경을 완전히 비우고
`HOME`·`PATH`·`AUTOPHAGY_REPO_ROOT`·더미 시크릿만 남긴 채 그 스킬의 `skills/hello-autophagy/scripts/scenario.sh`를
실행한다. 마지막으로 peer가 agent의 비밀 파일을 읽을 수 없는지까지 확인한다.

**성공 신호**

```text
[deploy-skill] scenario: SCENARIO-PASS secret_len=<n> account=<계정>
[deploy-skill] sandbox PASS (lint + discovery + dummy-secret scenario + isolation)
```

`hello-autophagy`의 시나리오는 더미 시크릿이 `DUMMY-` 접두를 갖는지, 진짜 토큰 모양이
아닌지, `skills/hello-autophagy/scripts/hello.sh` 출력에 `HELLO-AUTOPHAGY` 마커가 있는지를 강제한다.

### 11-2. 전체 파이프라인

```bash
bash automation/deploy-skill.sh hello-autophagy
```

진행 중 stderr에 단계 로그가 흐른다.

```text
[deploy-skill] stage 2/4 REVIEW (agent, deterministic hash-bound verdict)
[deploy-skill] review PASS (recorded hash-bound verdict)
[deploy-skill] stage 3/4 REQUEST + PEER-ATTEST + APPROVAL (#approvals)
[deploy-skill] approval request posted; peer attestation required
[deploy-skill] peer attestation PASS (posted by peer bot)
```

### 11-3. 소유자의 작업

개인 서버 `#approvals`에 올라온 메시지에 **✅** 리액션을 누른다. 취소는 **⛔**다. 봇이 두
이모지를 미리 붙여 두므로 탭 한 번이면 된다.

| 규칙 | 내용 |
|---|---|
| 유효한 리액션 | 소유자 본인의 비봇 리액션만 |
| 충돌 | ✅와 ⛔가 함께 있으면 ⛔가 이긴다 |
| 결속 | 승인은 실행 내용의 해시에 묶인다. 승인 뒤 내용이 바뀌면 실행되지 않는다 |
| 형식 | 텍스트 답장이 아니라 **리액션**이다 |

아직 ✅를 누르지 않은 상태에서 명령이 끝났다면, 아래 로그가 남고 exit 1로 끝난다. 메시지는
사라지지 않고 소유자를 기다린다.

```text
[deploy-skill] approval ABSENT or INVALID — NOT mounting (message <id> stays pending for the owner)
```

✅를 누른 뒤 같은 명령을 다시 실행하면, 게이트는 같은 요청을 재사용해 마운트까지 진행한다.
동일 요청에 승인 메시지를 두 개 만들지 않는 것이 이 시스템의 규칙이다.

**성공 신호**

```text
[deploy-skill] DEPLOYED hello-autophagy (sandbox→review→approval→mount complete; sandbox copy cleaned)
```

### 11-4. 배포되었는지 판정하는 법

**커밋됨 ≠ 배포됨.** 저장소 상태나 문서의 version이 아니라, `live` 심링크가 무엇을
가리키는지로 판정한다.

```bash
readlink "$(dirname "$AUTOPHAGY_SKILLS_ROOT")/live/hello-autophagy"
```

실제 호출까지 확인하려면:

```bash
bash ~/.hermes/skills/hello-autophagy/scripts/hello.sh
```

출력이 `HELLO-AUTOPHAGY`로 시작해야 한다.

### 11-5. 플래그와 종료 코드

| 플래그 | 의미 |
|---|---|
| `--sandbox-only` | 1단계까지만. 끝나면 peer의 사본을 지운다 |
| `--request-only` | attestation까지 하고 마운트하지 않는다. **표준출력에 메시지 ID만** 나온다 |
| `--approve-only` | 승인 확인까지 하고 마운트하지 않는다. `<메시지 ID>:<DEPLOY_NONCE>` 형태로 나온다 |
| `--fresh` | 살아 있는 기존 요청을 명시적으로 교체한다 |
| `--remove` | 활성 스킬을 제거한다 |
| `--activate-managed <격리 디렉터리>` | 관리형 스킬 활성화 전용 |

| 종료 코드 | 뜻 |
|---|---|
| 0 | 성공 |
| 1 | 승인이 없거나 무효 (마운트 안 함) |
| 2 | 샌드박스 차단 |
| 3 | 주간 자동 제안 상한 |
| 4 | 사용법·환경 오류 |
| 5 | 검토 누락·실패·해시 불일치 |
| 6 | 승인 생명주기 거부 (기존 라이브 요청 보존) |
| 8 | 다른 실행이 이 스킬의 리스를 점유 중 |

이미 게시된 요청을 이어서 마운트하려면 두 값이 모두 필요하다.

```bash
APPROVAL_MESSAGE_ID=... DEPLOY_NONCE=... bash automation/deploy-skill.sh hello-autophagy
```

`DEPLOY_NONCE`는 32자리 16진수여야 하며, 형식이 틀리면
`APPROVAL_MESSAGE_ID requires a valid DEPLOY_NONCE`로 중단한다. **`--request-only`는 nonce를
출력하지 않으므로**, 이 재개 경로를 쓸 생각이면 `--approve-only`를 쓰거나 그냥 전체 명령을
다시 실행한다(§15-7).

### 11-6. 배포 전 출처 검사

배포 스크립트는 시작 전에 `automation/deploy_provenance.sh`로 배포할 파일의 워킹트리 blob
해시를 배포 기준(`DEPLOY_PROVENANCE_REF`, 기본 `origin/main`)과 대조한다.

```text
OK: <n> file(s) match origin/main
```

불일치·미추적·미푸시는 모두 `DEPLOY-BLOCK:`으로 중단한다. 통과시키면 노드가 저장소에 없는
코드를 돌게 되고, 다음에 누군가 깨끗한 체크아웃에서 같은 스크립트를 돌리는 순간 그 변경이
말없이 되돌아간다. 탈출구 `DEPLOY_ALLOW_UNPUSHED=1`은 샌드박스 실험 전용이다.

## 단계 12 — 승인 워처(cron) 등록

> **왜.** 승인 메시지를 게시하는 것과 소유자의 ✅를 알아채는 것은 다른 일이다. 리액션을
> 폴링하는 워처가 없으면 승인 게이트는 열리지도 닫히지도 않고, 소유자가 눌러도 아무 일도
> 일어나지 않는다.

| | |
|---|---|
| 선행 조건 | 단계 9·10 완료(각 계정의 `~/.env.secrets`, interop 설정), 해당 스킬이 마운트됨 |
| 실행 계정 | 워크스테이션(`DEPLOY_SSH_HOST` 경유) |
| 무엇이 바뀌나 | `~/.hermes/scripts/`에 래퍼 파일, 그리고 cron 항목 |

### 12-1. 먼저 — 여기서 말하는 cron은 시스템 crontab이 아니다

> **정정.** 이 워처들은 **시스템 crontab(`crontab -e`·`/etc/cron.d`)에 등록되지 않는다.**
> 등록 대상은 **Hermes 자체의 cron 기능**이고, 확인도 `hermes cron list`로 한다. 시스템
> crontab을 아무리 뒤져도 아무것도 나오지 않으므로, "워처가 안 돌고 있다"고 판단하기 전에
> 반드시 이쪽을 먼저 본다. 엉뚱한 곳을 뒤지기 쉬운 자리다.

예외는 하나뿐이다. **수리 승인 워처만 cron이 아니라 systemd 서비스 + 타이머**로 돈다(§12-4).

### 12-2. 반드시 지키는 두 규칙

1. **워처는 리액션만 폴링한다.** 메시지·첨부의 수신과 처리는 실시간 에이전트의 단독
   영역이다. 둘이 같은 것을 소비하면 경쟁이 생기고 중복 실행이 난다.
2. **래퍼 파일 이름은 `~/.hermes/scripts/` 안에서 스킬별로 고유해야 한다.** 같은 이름을
   쓰면 나중에 배포한 쪽이 앞의 것을 덮어쓴다.

### 12-3. 전용 설치 스크립트가 있는 것

각 스크립트는 `DEPLOY_SSH_HOST`를 요구하고, 출처 검사 → 래퍼 복사 → cron 멱등 등록 →
`hermes cron list` 확인 순으로 진행한다.

| 명령 | cron 이름 | 주기 | 설치되는 래퍼 |
|---|---|---|---|
| `bash skills/calendar/deploy.sh` | `calendar-confirm-watch` | `*/1 * * * *` | `~/.hermes/scripts/calendar_confirm_reaction_watch.py` |
| `bash skills/coordination/deploy.sh` | `coordination-confirm-watch` | `*/1 * * * *` | `~/.hermes/scripts/confirm_reaction_watch.py` |
| `bash skills/mail/deploy.sh` | `mail-daily-digest` | `0 8 * * *` | `~/.hermes/scripts/mail_digest_watch.py` |
| `bash automation/drive_archive/deploy.sh` | `drive-archive-sync-request` | `every 1h` | `~/.hermes/scripts/drive_archive_sync_request.py` |
| (같은 스크립트가 함께 등록) | `drive-archive-confirm-watch` | `every 1m` | `~/.hermes/scripts/drive_archive_confirm_reaction_watch.py` |
| `bash automation/memory_curator/deploy.sh` | `memory-curator-watch` | `every 30m` | `~/.hermes/scripts/memory_curator_watch.py` |
| `bash automation/memory_relocate/deploy.sh` | `memory-relocate-watch` | `every 30m` | `~/.hermes/scripts/memory_relocate_watch.py` |

`automation/memory_relocate/deploy.sh`는 `AUTOPHAGY_DEPLOY_ROOT`도 요구한다.

**성공 신호.** 이 스크립트들은 고정된 성공 문자열을 찍지 않는다. 마지막에 실행되는
`hermes cron list`(일부는 `--all`) 출력에 위 표의 cron 이름이 보이면 등록된 것이다.

### 12-4. 전용 설치 스크립트가 **없는** 워처 (수동 등록)

아래 다섯은 저장소에 전용 cron 설치 스크립트가 없다. 각각을 쓰려면 직접 등록해야 한다.

| 워처 | 호출 형태 | 필요한 값 |
|---|---|---|
| `skills/mail/scripts/mail_triage_watch.py` | 마운트된 `triage_cli.py`를 `watch` 서브커맨드로 exec | `TRIAGE_*` 계열, `INTEROP_CONFIG`, `DISCORD_BOT_TOKEN` |
| `skills/budget/scripts/budget_watch.py` | 마운트된 `budget_cli.py`를 `watch` 서브커맨드로 exec | `BUDGET_*` 계열, `BUDGET_GWS_BIN`, `INTEROP_CONFIG`, `DISCORD_BOT_TOKEN` |
| `skills/wiki/scripts/wiki_confirm_reaction_watch.py` | 인자 없이 직접 실행 | `WIKI_ROOT`(기본 `~/wiki`), `WIKI_GATE_DIR`, `INTEROP_CONFIG`, `DISCORD_BOT_TOKEN` |
| `skills/patent-prep/scripts/patent_export_confirm_reaction_watch.py` | 인자 없이 직접 실행 | `PATENT_EXPORT_ROOT`, `AUTOPHAGY_PRIVATE_ROOT`, `DISCORD_BOT_TOKEN` |
| `automation/repair/repair_ops_reaction_watch.py` | 인자 없이 직접 실행 | `DISCORD_BOT_TOKEN`, `DISCORD_OWNER_ID`, `AUTOPHAGY_PRIVATE_ROOT`, `AUTOPHAGY_DEPLOY_ROOT` |

운영 중 확인된 등록 형태는 아래와 같다. 등록 명령까지 남아 있는 것과 그렇지 않은 것이 갈린다.

| 워처 | 확인된 등록 형태 |
|---|---|
| 메일 분류 | Hermes cron |
| 예산 | Hermes cron |
| 비용 리포트(`automation/cost-report/send_cost_report.py`) | Hermes cron, 하루 1회 |
| 리마인더 폴러(`automation/reminder_poller/poll_reminders.py`) | Hermes cron, 수 분 간격 |
| 위키 확인 | **등록 명령이 남아 있지 않다**(§15-3) |
| 특허 반출 확인 | **등록 명령이 남아 있지 않다**(§15-3) |
| 수리 승인 | cron이 아니라 systemd 서비스 + 타이머 |

이들 다수는 `--no-agent` 형태로 등록됐다 — 에이전트 세션 없이 도는 작업이라는 뜻이다.
그래서 환경에 비밀이 주어지지 않고, 워처가 자격증명을 스스로 읽어 자식에게 명시 전달해야
한다(§9-1).

수리 워처만은 예외적으로 systemd 유닛 템플릿이 있다 —
`automation/repair/systemd/autophagy-repair-approval-watch.service`와
`automation/repair/systemd/autophagy-repair-approval-watch.timer`(1분 주기, `User=ops`).
`%%…%%` 자리표시자를 환경 계약의 값으로 렌더링해 설치한다.

등록할 때는 위 두 규칙(리액션만, 고유 파일명)과 자격증명 명시 전달 규약을 지킨다. 상세:
[Watcher-Cron 설계 규약](guide/watcher-cron-설계규약.md).

## 13. 최소 동작 승인 루프 — 전부 갖추지 않아도 시작할 수 있다

승인 한 사이클을 닫는 데 실제로 필요한 것은 네 가지뿐이다.

| # | 필요한 것 | 어디서 |
|---|---|---|
| ① | 승인 요청을 만드는 스킬 CLI | 예: `skills/wiki/scripts/wiki_cli.py` |
| ② | 승인 생명주기(리스·저널·pending 저장) | `automation/interop/` |
| ③ | 같은 표면을 폴링하는 리액션 전용 워처 **하나** | 예: `skills/wiki/scripts/wiki_confirm_reaction_watch.py` |
| ④ | Discord에서 소유자의 ✅ / ⛔ | 사람 |

**필요 없는 것**: `automation/deploy-skill.sh`, `automation/healthcheck.sh`,
`automation/land.sh`, 릴리스 저장소, RAG 스택, managed-sync, 메모리 큐레이터, 그 밖의 모든
cron. Google도 필요 없다.

### 13-1. 최소 경로

| 단계 | 하는 일 |
|---|---|
| 1 | 로컬 체크아웃 검증 |
| 2 | Discord 봇 1개 + 소유자 DM (이 루프에는 peer 봇도 `#approvals`도 필요 없다) |
| 5 | `.env`의 채팅 신원 6개 + `DISCORD_BOT_TOKEN` |
| 6 | 노드 계정 부트스트랩 |
| 9 | `~/.env.secrets`와 `~/.hermes/interop/config.json`(최소 `owner_id`) |
| 10 | `agent` 게이트웨이 프로비저닝 |
| §12-4 | 워처 **하나만** 등록 |

### 13-2. 한 바퀴 돌려 보기

위키 스킬은 외부 서비스에 접근하지 않고 로컬 노트만 쓴다. 그래서 첫 루프 대상으로 적합하다.

```bash
# ① 초안을 만든다 — 이 시점에 위키에는 아무것도 쓰이지 않는다
python3 skills/wiki/scripts/wiki_cli.py draft --title "첫 노트" --tags demo --body "본문"

# ② 소유자 DM에 올라온 확인 메시지에 ✅ 를 누른다

# ③ 워처가 그 리액션을 보고 저장을 수행한다 (또는 확인 명령을 직접 실행한다)
python3 skills/wiki/scripts/wiki_cli.py confirm --draft <초안 ID>
```

이 한 바퀴가 돌면 승인 불변식이 실제로 살아 있다는 뜻이다. 나머지 기능은 같은 게이트에
스킬을 하나씩 얹는 일이다.

## 14. 운영

### 14-1. 상태 점검

점검 자체는 읽기 전용이다. 다만 **스크립트를 손으로 직접 부르지 않고 전용 래퍼를 거쳐
실행하는 것**이 운영 중 확인된 방식이었다 — 래퍼 안에서 타임존과 SSH 신원 파일을 함께
고정한다.

| 항목 | 운영 중 확인된 방식 |
|---|---|
| 실행 | 전용 래퍼를 거쳐 실행 (환경을 매번 손으로 맞추지 않는다) |
| 타임존 | 래퍼가 명시 지정 |
| SSH 신원 | `HEALTHCHECK_SSH_IDENTITY`로 **점검 전용의 제한된 키**를 지정 |

> **점검용 SSH 키는 배포 키를 재사용하지 않는다.** 점검은 읽기만 하면 되므로 권한을 더
> 좁힌 별도 키를 둔다. 키 하나가 새면 그 키가 할 수 있는 일의 범위가 곧 피해 범위다.

```bash
bash automation/healthcheck.sh
```

아래 `HEALTHCHECK_*` 값이 모두 있어야 시작한다.

| 변수 | 뜻 |
|---|---|
| `HEALTHCHECK_LOG_DIR` | 로그 디렉터리 |
| `HEALTHCHECK_HOST_A` / `_HOST_B` | 1차 / 2차 서비스 호스트 |
| `HEALTHCHECK_SSH_USER` | 프로브가 쓸 SSH 계정 |
| `HEALTHCHECK_DASHBOARD_AUTH_URL` | 미인증 요청을 401로 거부해야 하는 URL |
| `HEALTHCHECK_OPS_CHECKOUT` | 미러 드리프트를 볼 배포 체크아웃 |
| `HEALTHCHECK_REPAIR_CLI` / `_REPAIR_ACCOUNT` | 수리 CLI 경로와 실행 계정 |
| `HEALTHCHECK_MCP_COLLECTION` | 존재를 확인할 검색 컬렉션 이름 |

`HEALTHCHECK_SSH_IDENTITY`는 문법상 선택이고 미설정 시 기본 키 경로를 쓴다. 다만 위 이유로
**비워 두지 않기를 권한다.** 각 변수의 구체값은 설치별 운영 설정이라 저장소 밖에 있다(§15-5).

검사 순서는 모델 게이트웨이 응답 → `agent` 게이트웨이 active → `peer` 게이트웨이 active →
임베딩 → 벡터DB → MCP → 리포트 허브 수집기 → 대시보드 → 대시보드 미인증 401 거부 →
배포 체크아웃의 미러 정합이다.

**성공 신호** — 개별 `PASS` 줄이 이어지다가 마지막에 `ALL_HEALTHY`가 나오고, 종료 코드는 0이다.

```text
PASS <검사 이름>
PASS <검사 이름>
...
ALL_HEALTHY
```

프로브 자체가 도는지 보고 싶으면 `--synthetic-failure`로 일부러 실패하는 검사를 하나 넣어
실행할 수 있다.

**검사가 한꺼번에 전부 실패하면 개별 서비스보다 먼저 공통 SSH 경로를 의심한다**(§17-4).

### 14-2. 배포 순서 규율

**검토 가능한 변경 → 원격 반영 → 배포 → 실제 검증.** 순서를 바꾸면 출처 가드가 배포를
막는다. 그 막힘 자체가 프로덕션 수정본 유실을 방지하는 장치다.

| 대상 | 반영 방법 |
|---|---|
| 스킬 | `automation/deploy-skill.sh`(4단계 게이트) |
| 워처 | 각 `deploy.sh` (§12-3) 또는 수동 등록 (§12-4) |
| 노드에서 도는 automation 코드 | `automation/land.sh` |
| 문서·테스트만 바뀐 경우 | 반영할 것이 없다 |

### 14-3. 배포 체크아웃은 단방향 거울

허용되는 쓰기는 `git fetch`와 `git pull --ff-only`뿐이다. 편집·`git add`·`git commit`·
`git stash`는 금지되고, 단계 6이 설치한 훅이 커밋을 무조건 거부한다.

드리프트 탐지는 `automation/checkout_mirror_probe.sh`가 담당한다. 판정값은 다음과 같다.

| 판정 | 뜻 |
|---|---|
| `mirror-clean` | 정상(유일하게 exit 0) |
| `mirror-dirty` | 추적 파일에 미커밋 변경 |
| `mirror-ahead` | 그 안에서 커밋이 만들어졌다 |
| `mirror-behind` | 기준보다 뒤처짐 |
| `mirror-unknown-remote` | 원격을 읽지 못함(프로브는 `git fetch`를 하지 않는다) |
| `mirror-no-checkout` | 체크아웃 자체가 없음 |

**복구는 파괴적으로 하지 않는다.** 앞서 있는 커밋은 `git format-patch` → 개발 체크아웃에서
`git am` → push → 노드에서 `git pull --ff-only` 순으로 작성자·타임스탬프를 보존한 채 올린다.
`git reset --hard`·`git checkout --`·`git stash`를 먼저 쓰면 그 작업분이 사라진다. 프로브는
실패할 때 이 절차를 그대로 출력한다.

### 14-4. 판정은 언제나 실물로

| 질문 | 판정 방법 |
|---|---|
| 이 스킬이 배포됐나 | `readlink <스토어>/live/<스킬>` |
| 런타임이 어느 코드를 도나 | 릴리스 `current`가 가리키는 SHA (§8-3) |
| 워처가 도나 | `hermes cron list`와 마지막 실행 결과 |
| 게이트웨이가 사나 | `systemctl --user is-active hermes-gateway.service` |

### 14-5. 원인 확인이 먼저

정상 서비스는 확인 목적으로 재시작하지 않는다. 원인을 알기 전에 설정·키·네트워크 규칙을
바꾸지 않는다. 증상을 보면 반사적으로 하게 되지만 상황을 악화시키는 행동은 §16에, 실제로
발생했던 장애와 그 조치는 §17에 모아 두었다. 그 밖의 증상별 판단은
[장애 대응](guide/incident-response.md), 재부팅 이후는
[재부팅 복구 절차](guide/reboot-recovery.md)를 따른다.

## 15. 이 저장소가 답해주지 않는 것

아래 항목은 저장소를 아무리 읽어도, 그리고 운영 기록을 뒤져도 답이 나오지 않는 지점이다.
대부분 **처음 설치할 때 반드시 마주치므로** 미리 알고 가는 편이 낫다.

이전에 이 표에 있던 항목 상당수는 이제 각 단계 본문으로 옮겨 갔다 — Discord scope와
권한(§2-2), 두 봇의 토큰이 어떻게 갈리는가(§2-5), Google OAuth 클라이언트 타입과
scope(§3-1), `gws` CLI 설치와 인증 산출물(§3-2·§3-3), 게이트웨이 스택이 요구하는 값(단계 4),
승인 채널 해석 순서(§9-2), 게이트웨이 설정 파일의 형태(§10-4), 워처가 어느 cron에
등록되는가(§12-1). **답이 있는 정보는 그 단계를 수행하는 시점에 읽는 편이 낫기 때문에**
이 공백 목록에 남기지 않았다.

| # | 공백 | 어디서 막히나 | 어떻게 우회·조달하나 |
|---|---|---|---|
| 1 | **게이트웨이 설치 URL에 버전 핀이 없다.** `automation/provision-agent.sh`가 외부 설치기 URL을 호출할 뿐이고 체크섬 검증도 없다 | 단계 10. 어제와 다른 버전이 깔려도 알 수 없고, 설치기가 바뀌거나 사라지면 게이트웨이를 만들 수 없다 | 설치 직후 실제 버전을 기록해 두고, 재구축할 때 같은 버전인지 대조한다(§10-2). 재현이 필요하면 설치 산출물을 스냅샷으로 보관한다 |
| 2 | **Discord permission 정수값이 없다.** 초대 URL의 `permissions=<정수>`에 넣을 값이 저장소에도 운영 기록에도 보존돼 있지 않다 | 단계 2. 봇 초대 URL을 만들 때 | §2-2의 체크박스 목록을 Discord 개발자 포털의 URL 생성기에서 고르면 정수가 자동 계산된다. 손으로 계산하지 않는다 |
| 3 | **위키 확인 워처와 특허 반출 확인 워처의 실제 cron 등록 명령이 없다.** 다른 워처는 등록 형태가 확인됐지만 이 둘은 남아 있지 않다 | 그 두 기능의 승인이 영영 닫히지 않는다. 소유자가 ✅를 눌러도 아무 일이 없다 | §12-4의 호출 형태와 필요한 값을 보고 **Hermes cron에** 직접 등록한다(시스템 crontab이 아니다, §12-1). 래퍼 파일명은 고유해야 하고, 자격증명은 자식 프로세스에 명시 전달한다 |
| 4 | **검색 스택의 디스크 용량과 임베딩 서버 패키지 설치 상세가 없다.** CPU 추론 여부와 메모리 기준선은 §2.3에 있지만 이 둘은 어느 기록에도 없다 | RAG를 쓰려는 시점 | 검색 스택은 선택이다. 없으면 `recall`이 검색 불가로 degrade하고 인제스트는 큐에 남으며, 승인 경로는 계속 동작한다. 일반적인 판단 근거는 [DGX Spark 활용 검토](spark-활용-검토.md)에 있다 |
| 5 | **`HEALTHCHECK_*`의 실제 값이 저장소 밖에 있다.** 설치별 운영 설정이기 때문이다 | 단계 14-1. 값이 다 없으면 스크립트가 시작조차 하지 않는다 | 노드·계정·URL·컬렉션 이름을 확정한 뒤 비공개 인벤토리에 기록한다. 스키마는 [`configs/inventory.example.yaml`](../configs/inventory.example.yaml). SSH 신원은 점검 전용 키로 따로 둔다(§14-1) |
| 6 | **스킬 스토어 경로가 두 곳에서 따로 정해진다.** `.env`의 `AUTOPHAGY_SKILLS_ROOT`와 `automation/provision-readonly-skills.sh` 안의 고정 경로 | 단계 7·11. 둘이 어긋나면 승인까지 다 통과한 뒤 마운트 지점에서 어긋난다 | `AUTOPHAGY_SKILLS_ROOT`를 그 스크립트가 만드는 스토어의 `live` 디렉터리로 맞춘다. 확정 전에 스크립트 상단의 경로 상수를 직접 읽어 확인한다 |
| 7 | **`--request-only`가 nonce를 출력하지 않는다.** 재개에는 메시지 ID와 nonce가 둘 다 필요하다 | 단계 11-5. 요청만 걸어 두고 나중에 마운트하려다 막힌다 | `--approve-only`를 쓰거나(둘 다 출력한다), 승인 후 전체 명령을 다시 실행한다. 게이트가 같은 요청을 재사용하므로 메시지가 중복 생성되지 않는다 |

## 16. 위험한 반사행동 — 하기 전에 멈춘다

> **아래 아홉 가지는 증상을 보면 반사적으로 하게 되지만, 거의 언제나 상황을 악화시킨다.**
> 공통점은 하나다 — **원인을 확인하기 전에 상태를 바꿔 버린다.** 상태를 바꾸는 순간 진단에
> 필요한 증거가 사라지고, 그다음부터는 처음 문제와 내 조치가 만든 문제를 구분할 수 없다.

| 하지 않는다 | 왜 나쁜가 |
|---|---|
| 건강한 서비스를 "확인차" 재시작하기 | 원인을 지우고 재현을 어렵게 만든다 |
| 게이트웨이를 한쪽만 재시동하기 | 짝이 어긋나 승인·인증이 조용히 타임아웃된다 |
| 체크아웃을 `reset --hard`로 먼저 맞추기 | 아직 추출하지 않은 작업물을 지운다 |
| 인증 실패를 자동 재시도하기 | 계정 잠금을 부른다 |
| 스킬 본체 없이 워처만 재배포하기 | 옛 코드가 남아 원인 불명 실패가 계속된다 |
| 런타임 상태를 추적 파일에 쓰기 | 다음 배포 정렬에서 조용히 유실되고, 그때까지 pull이 막힌다 |
| 배포 체크아웃 안에서 편집·커밋하기 | 원격에 도달하지 못한 코드가 프로덕션에 남는다 |
| 승인 메시지를 다시 게시하거나 기존 메시지 ID를 덮어쓰기 | 소유자가 누른 승인이 고아가 된다 |
| 원인 확인 전에 설정이나 키를 바꾸기 | 변수를 늘려 진단을 불가능하게 만든다 |

## 17. 증상별 대처

아래는 실제로 발생했던 장애를 일어난 단계별로 묶은 것이다. 각 항목은 **증상 / 원인 / 조치 /
예방** 네 줄로 적는다.

### 17-1. 설치 중

**① 설치 바이너리가 노드 아키텍처와 맞지 않는다**

- **증상** — 설치가 실패로 끝나고, 대체 경로가 자동으로 실행되지 않는다.
- **원인** — ARM 계열 노드에 x86 절차를 그대로 사용했다.
- **조치** — 문서가 안내하는 컨테이너 대체 경로로 전환한 뒤 다시 실행한다.
- **예방** — 설치 전에 `uname -m`으로 아키텍처를 확인한다.

### 17-2. 설정 중

**② 런타임 상태를 추적 파일에 썼다**

- **증상** — 체크아웃이 더러워지고 `git pull --ff-only`가 막힌다.
- **원인** — 런타임에 변하는 값을 저장소가 추적하는 설정 파일에 썼다.
- **조치** — 런타임 상태를 체크아웃 밖으로 옮기고 추적 파일을 원복한다.
- **예방** — 추적되는 설정은 **읽기 전용 시드**로만 취급한다. 변하는 것은 전부 밖에 둔다.

**③ 외부 서비스 로그인 실패가 모호한 인증 오류로 표시된다**

- **증상** — 어떤 값이 틀렸는지 알 수 없는 일반적인 인증 실패만 돌아온다.
- **원인** — 비밀값 부재·절단·잔여 세션 등 여러 가능성이 같은 메시지로 접힌다.
- **조치** — 비밀값의 존재와 길이를 확인 → 잔여 세션을 정리 → 수동 로그인으로 검증 →
  반복되면 에스컬레이션한다.
- **예방** — **인증 실패는 자동 재시도하지 않는다.** 재시도는 계정 잠금으로 이어진다.

**④ 외부 서비스의 화면 구조가 바뀌어 동기화가 중단됐다**

- **증상** — 직전까지 잘 돌던 동기화가 어느 시점부터 아무것도 가져오지 못한다.
- **원인** — 셀렉터 계약이 깨졌다. 상대방의 화면 구조가 바뀐 것이다.
- **조치** — **같은 요청을 반복하지 않는다.** 이건 일시적 오류가 아니라 구조적 실패라,
  셀렉터를 고치기 전까지는 몇 번을 돌려도 같은 결과다.
- **예방** — 재시도해서 나아지는 오류와 구조적 실패를 처음부터 다른 분류로 다룬다.

### 17-3. 배포 중

**⑤ 체크아웃 pull 권한이 계정 역할과 어긋난다**

- **증상** — 한 계정은 저장소를 못 찾고, 다른 계정은 객체 디렉터리 쓰기가 거부된다.
- **원인** — 배포 키를 가진 계정이 그룹 권한에서 빠져 있었다.
- **조치** — 계정을 올바른 그룹에 넣고, 체크아웃 권한을 그룹 쓰기 가능하게 정렬한다.
- **예방** — pull 주체와 저장소 소유권을 일치시킨다.

**⑥ 커밋·푸시하지 않은 코드가 배포됐다**

- **증상** — 배포 후 코드가 조용히 되돌아간다. 아무 오류도 나지 않는다.
- **원인** — 미커밋 파일, 미푸시 커밋, 뒤처진 체크아웃, 또는 디렉터리 안의 추적되지 않은 새
  파일이 검사를 우회했다.
- **조치** — 배포 전 출처 검사로 원격 기준과 blob 해시를 대조한다(§11-6).
- **예방** — **커밋 → 푸시 → 배포** 순서를 고정한다. 순서를 바꾸면 가드가 막는데, 그 막힘이
  바로 유실 방지 장치다.

**⑦ 워처만 재배포하고 스킬 본체를 빼먹었다**

- **증상** — cron이 "알 수 없는 명령" 류 오류로 실패한다.
- **원인** — 워처만 새로 깔리고, 그가 호출하는 스킬 본체는 옛 버전 그대로다.
- **조치** — 스킬 전체를 다시 배포하고 `live` 심링크가 새 해시를 가리키는지 확인한다(§11-4).
- **예방** — 스킬 코드 변경은 배포 완료까지가 한 단위다. 워처만 따로 밀지 않는다.

**⑧ 승인이 실제 실행 대상과 다른 내용에 묶였다**

- **증상** — 소유자가 본 것과 실제 실행된 것이 다르거나, 누른 ✅가 아무런 효력을 내지 못한다.
- **원인** — 이름만 해싱했거나 기존 메시지 ID를 덮어써서 승인과 근거가 분리됐다.
- **조치** — 승인을 이름이 아니라 **바이트**에 바인딩하고, 메시지 재사용·덮어쓰기를 금지한다.
- **예방** — 승인 생명주기는 내용 바인딩된 단일 경로만 쓴다. 동일 논리 요청에 라이브 메시지는
  정확히 하나다.

### 17-4. 운영 중

**⑨ 컨테이너가 좀비 프로세스를 남긴다**

- **증상** — 종료된 프로세스가 정리되지 않고 계속 쌓인다.
- **원인** — 컨테이너의 PID 1이 애플리케이션 자신이라 고아 프로세스를 회수하지 못한다.
- **조치** — compose에 init 회수 프로세스를 넣고 컨테이너를 재생성한다.
- **예방** — 장수 컨테이너는 자식을 만들 가능성을 전제하고 설계한다.

**⑩ 게이트웨이를 한쪽만 재시동해 승인·인증이 타임아웃됐다**

- **증상** — 재시동한 쪽은 살아나는데 승인과 attestation이 조용히 만료된다.
- **원인** — 승인 경로가 두 게이트웨이의 짝을 전제로 하는데 한쪽만 살아나면 반쪽이 된다.
- **조치** — 모델 게이트웨이 상태를 먼저 확인한 뒤, **행위 봇과 peer 봇의 게이트웨이를 함께**
  재시동한다. 재시동 창에 걸린 요청은 재요청한다(차단이 아니다).
- **예방** — 게이트웨이 재시동은 항상 짝으로. 이 규칙은 재시동이 결정된 **뒤의 범위**만
  정한다 — 건강한 서비스를 재시동하지 않는다는 원칙은 그대로다(§16).

**⑪ 상태 점검이 한꺼번에 전부 실패한다**

- **증상** — 개별 프로브가 하나도 빠짐없이 실패한다.
- **원인** — **원인이 개별 서비스가 아니라 공통 SSH 경로일 수 있다.** 모든 것이 동시에
  고장나는 일은 드물고, 보통은 그것들을 보러 가는 길이 끊긴 것이다.
- **조치** — 표준 래퍼와 기본 환경으로 다시 실행해 공통 경로부터 배제한다(§14-1).
- **예방** — 점검은 항상 문서화된 래퍼로만 실행한다. 그래야 실패가 환경 차이인지 서비스
  문제인지를 구분할 수 있다.

**⑫ 검색 스택이 죽었다 — 적재분은 유실되지 않는다**

- **증상** — 색인이 멈춘 듯이 보이고 검색이 빈 결과를 돌려준다.
- **원인** — 설계상 다운 상태에서는 큐에 쌓고 재시도한다. 멈춘 것처럼 보일 뿐 손실은 없다.
- **조치** — 서비스를 복구한 뒤 다음 tick을 기다린다.
- **예방** — **다운 중에 수동 재색인하지 않는다.** 내구 큐를 믿는다 — 손으로 밀어 넣으면
  중복 적재와 순서 어긋남만 늘어난다.

### 17-5. 그 밖의 흔한 증상

| 증상 | 흔한 원인 | 확인 / 조치 |
|---|---|---|
| 부트스트랩이 배너만 찍고 끝난다 | 정상이다. 사람 작업 대기 중 | 배포 키를 읽기 전용으로 등록하고 재실행 (§6-2) |
| `GitHub deploy-key auth OK`가 안 나온다 | 키 미등록, 또는 잘못된 저장소에 등록 | 등록 페이지를 다시 확인. `Allow write access`는 계속 체크하지 않는다 |
| `provision-agent.sh`가 즉시 중단된다 | 비밀 파일 소유자·모드, 또는 빈 키 | 메시지가 어떤 검사인지 그대로 말해 준다 (§10-1) |
| 게이트웨이가 `active`가 아니다 | linger 미활성, 모델 게이트웨이 무응답 | linger 확인 후 `is-active`·`status`로 진단. 재시동은 agent·peer를 **함께** (§17-4 ⑩) |
| 승인 메시지가 안 온다 | interop 설정 없음, 토큰 오배치 | §9-2와 §2-5를 확인 |
| ✅를 눌렀는데 아무 일도 없다 | 그 흐름의 리액션 워처가 없다 | §12-4에서 해당 워처를 Hermes cron에 등록 (§12-1) |
| 승인이 엉뚱한 채널로 간다 | 채널을 `.env`로 지정하려 했다 | `~/.hermes/interop/config.json`으로 지정 (§9-2) |
| `approvals channel is absent or ambiguous across guilds` | 봇 시야에 `approvals` 채널이 0개 또는 2개 이상 | 공유 서버의 동명 채널을 없애거나 config에 ID를 명시 |
| 배포가 `DEPLOY-BLOCK`으로 멈춘다 | 미커밋·미푸시 코드를 배포하려 했다 | 커밋 → 푸시 → 배포 순서로 되돌린다 (§17-3 ⑥) |
| 마운트 직전에 실패한다 | root 헬퍼·sudoers 미설치, 또는 스토어 경로 불일치 | 단계 7 재실행, `AUTOPHAGY_SKILLS_ROOT` 확인 (§15-6) |
| 코드를 고쳤는데 동작이 그대로다 | 커밋만 하고 반영하지 않았다 | `readlink`로 실물 판정 (§14-4). "커밋됨 ≠ 배포됨" |
| 노드에서 `git pull --ff-only`가 막힌다 | 그 체크아웃에서 커밋이 생겼다 | `mirror-ahead`. 비파괴 복구 절차 (§14-3) |
